# Dynatrace Day 1 — Fundamentals

## 1. What is Dynatrace?

Dynatrace is an **observability and Application Performance Monitoring (APM) platform**.

It helps monitor and troubleshoot:

* Applications
* Services
* Servers/Hosts
* Processes
* Kubernetes
* Databases
* Logs
* Metrics
* Distributed traces
* External dependencies

### Main purpose

```text
Detect → Analyze → Find Root Cause → Resolve
```

Example:

A customer reports:

> "The OTT application is slow."

Dynatrace can help us investigate:

```text
User
 ↓
Application
 ↓
Service
 ↓
Request / Trace
 ↓
Database / External API
 ↓
Infrastructure
 ↓
Logs + Metrics
 ↓
Root Cause
```

---

# 2. What is Observability?

Observability is the ability to understand the internal state and behavior of a system by analyzing the data it produces.

The three major pillars are:

```text
Metrics
Logs
Traces
```

---

# 3. Metrics

Metrics are numerical measurements that tell us about the health and performance of a system.

Examples:

```text
CPU Usage       = 85%
Memory Usage    = 72%
Response Time   = 3.5 seconds
Error Rate      = 5%
Request Rate    = 10,000 requests/min
```

### Why are metrics useful?

They help identify:

* High CPU
* High memory usage
* Increased response time
* Increased error rate
* Traffic spikes
* Resource saturation

### Example

If CPU suddenly changes:

```text
CPU
100% |                 █
 80% |              █  █
 60% |          █   █  █
 40% |     █    █   █  █
 20% | █   █    █   █  █
     +--------------------
          Time
```

This could indicate increased traffic or a resource-related problem.

---

# 4. Logs

Logs are detailed records generated by applications, servers and other components.

Example:

```text
2026-10-06 18:10:21
ERROR PlaybackService
Connection timeout to database
```

Logs can provide information about:

* Errors
* Warnings
* Exceptions
* Timeouts
* Authentication failures
* Application events
* Configuration issues

### Example production investigation

Customer reports:

> "Playback is not working."

A log might show:

```text
ERROR
Database connection timeout
```

This gives us a possible direction for further investigation.

---

# 5. Traces

A trace shows the journey of a request through an application and its dependencies.

Example:

```text
User Request
     ↓
Playback API
     ↓
Authentication Service
     ↓
Content Service
     ↓
Database
```

Example timing:

```text
Playback API          5,000 ms
 ├── Authentication     100 ms
 ├── Content Service    200 ms
 └── Database         4,700 ms
```

The application takes 5 seconds overall, but the database takes 4.7 seconds.

Therefore, the database is a strong candidate for the root cause.

---

# 6. Metrics vs Logs vs Traces

| Type    | What it tells us             | Example           |
| ------- | ---------------------------- | ----------------- |
| Metrics | How much / how often         | CPU = 90%         |
| Logs    | What happened                | Database timeout  |
| Traces  | Where the request spent time | DB call = 4.7 sec |

They complement each other.

```text
Metrics
   ↓
Something is wrong
   ↓
Traces
   ↓
Where is it happening?
   ↓
Logs
   ↓
What happened?
   ↓
Root Cause
```

# 7. What is OneAgent?

**OneAgent is Dynatrace's monitoring agent.**

It is installed on a monitored host and collects information about the environment.

Conceptually:

```text
Linux Server
     │
     └── OneAgent
           │
           ├── Processes
           ├── Applications
           ├── Services
           ├── Metrics
           ├── Traces
           └── Logs
                    │
                    ↓
               Dynatrace
```

OneAgent helps Dynatrace automatically discover applications, services, processes and dependencies.

We will learn OneAgent installation and architecture in detail on **Day 2**.

---

# 8. What is a Host?

A host is a machine/server on which applications or services run.

Example:

```text
Server-01

OS: Linux
CPU: 8 cores
Memory: 16 GB
IP: 10.x.x.x
```

Dynatrace can monitor:

* CPU
* Memory
* Disk
* Network
* Processes
* Availability

---

# 9. What is a Process?

A process is a running program on a host.

Example:

```text
Linux Server
     |
     ├── nginx
     ├── java
     ├── node
     └── python
```

Dynatrace can monitor processes and their resource consumption.

---

# 10. What is a Service?

A service is a software component that performs a particular function.

For example, an OTT platform could have:

```text
OTT Application
      |
      ├── Login Service
      ├── Content Service
      ├── Playback Service
      ├── Payment Service
      └── Recommendation Service
```

If the customer reports a playback issue, we can investigate the **Playback Service**.

---

# 11. What is an Application?

An application is generally something that the end user interacts with.

Examples:

* Web application
* Mobile application
* Smart TV application
* OTT application

Example:

```text
Customer
   ↓
Smart TV App
   ↓
Playback API
   ↓
Playback Service
```

---

# 12. Important Mental Model

A simple beginner mental model is:

```text
USER
 ↓
APPLICATION
 ↓
SERVICE
 ↓
PROCESS
 ↓
HOST
```

However, real environments are more complex.

A service can communicate with:

```text
Service
 ├── Database
 ├── Other Service
 ├── External API
 └── Message Queue
```

Dynatrace helps visualize these relationships.

---

# 13. What is Topology?

Topology represents the relationships and dependencies between components.

Example:

```text
                OTT Application
                       |
                Playback Service
                 /            \
                /              \
        Content Service      Database
              |
          External API
```

This is useful during troubleshooting because we can identify which components depend on each other.

---

# 14. Dynatrace vs Prometheus/Grafana/Kibana

The tools solve different parts of observability.

| Tool       | Main Purpose                        |
| ---------- | ----------------------------------- |
| Prometheus | Metrics collection/storage/querying |
| Grafana    | Dashboards and visualization        |
| Promtail   | Log collection                      |
| Loki       | Log aggregation/storage             |
| Kibana     | Log search/visualization            |
| Dynatrace  | End-to-end observability/APM        |

A typical existing monitoring architecture might be:

```text
Application
     ↓
Log File
     ↓
Promtail
     ↓
Loki
     ↓
Grafana
```

Another:

```text
Application
     ↓
Metrics
     ↓
Prometheus
     ↓
Grafana
```

Dynatrace can provide a more integrated view:

```text
                 Dynatrace
                     ↑
                  OneAgent
                     ↑
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
     Metrics        Logs         Traces
       │             │             │
       └─────────────┼─────────────┘
                     ↓
          Applications / Services
                     ↓
             Infrastructure
```

# 15. Why is Dynatrace useful for Production Support?

Production support often starts with a symptom.

Example:

> Customer reports that the application is slow.

We need to answer:

* Is the application available?
* Is response time high?
* Which service is slow?
* Which request is slow?
* Is a database causing the delay?
* Is an external API slow?
* Is CPU high?
* Is memory high?
* Are there errors in the logs?
* Did something change recently?

Dynatrace can correlate these different types of information.

---

# 16. Basic Production Troubleshooting Flow

When investigating an incident:

```text
1. Identify the affected application
             ↓
2. Check availability
             ↓
3. Check response time
             ↓
4. Identify affected service
             ↓
5. Investigate requests/traces
             ↓
6. Check dependencies
             ↓
7. Check infrastructure
             ↓
8. Check logs
             ↓
9. Identify root cause
             ↓
10. Apply/coordinate resolution
             ↓
11. Verify recovery
```

---

# 17. Example — OTT Production Incident

### Problem

Customer reports:

> "Video playback is taking a long time to start."

### Investigation

```text
OTT Application
       ↓
Playback Service
       ↓
Playback API
       ↓
Content Service
       ↓
Database
```

Suppose Dynatrace shows:

```text
Playback API       5 sec
Authentication     100 ms
Content Service    200 ms
Database           4.7 sec
```

The database is consuming most of the request time.

Next steps:

1. Investigate database performance.
2. Check database-related logs.
3. Check database connection errors/timeouts.
4. Check infrastructure metrics.
5. Check whether there was a recent change.
6. Confirm whether other services are affected.
7. Identify root cause.
8. Verify recovery after remediation.

# 19. Day 1 Key Takeaways

Remember these five points:

### 1.

> Dynatrace is an **observability + APM platform**.

### 2.

> The three major observability pillars are **metrics, logs and traces**.

### 3.

> **OneAgent** collects monitoring information from the environment.

### 4.

> Dynatrace provides visibility across **applications, services, infrastructure and dependencies**.

### 5.

> The goal during production troubleshooting is not just to detect the problem, but to **identify the root cause**.
